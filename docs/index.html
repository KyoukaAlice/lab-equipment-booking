01它解决什么问题

高校贵重仪器（示波器、GPU 服务器、3D 打印机…）的共享存在四个典型痛点，本系统逐条给出工程解法。

⚠时段靠"接龙"占位

纸质登记本/微信群无法判断冲突，常出现两人同抢一台设备。
解法：R01~R12 规则引擎 + 区间重叠检测，冲突时返回冲突时段与占用者。

🕒约了不来，时段空转

预约成功却不到场，黄金时段被浪费。
解法：6 位签到码 + 签到时间窗；超期未签到由后台作业判定爽约、扣信用分并释放时段。

🔧维修/教学与预约撞车

计量校准、假期封闭、厂家维护等不可用时段没有纳入统一约束。
解法：停机计划作为区间差集的减项参与校验（R09），创建时自动通知受影响预约人。

📊没有可信的利用率数据

无法回答"哪台设备闲置、哪个时段是高峰"。
解法：利用率以真实排班开放时长为分母推导，配套热力图、趋势、履约率与 CSV 导出。

02核心能力

三类角色各自看到该看的：学生预约使用、教师审批、管理员掌握全局。

🎓学生 / 教师

  • 设备目录：按实验室、类别、状态、关键字检索，显示今日/本周剩余空闲
  • 可视化选时段：一周时间轴，15 分钟吸附，空闲/待审批/已通过/使用中/停机分色
  • 提交预约：R01~R12 全量校验，失败给出可执行提示（如引导加入候补）
  • 现场签到（6 位码 + 时间窗）与签退（记录实际使用时长）
  • 候补队列：时段释放后自动补位 + 限时确认，超时自动顺延
  • 信用分台账、违约记录、本周额度；到期未签退自动记超时违约

✅实验室负责人

  • 审批中心：只能审批所辖实验室/设备的预约，且不得审批自己的预约
  • 批量通过 / 批量驳回（驳回必须填写原因）
  • 审批通过自动生成签到码并通知申请人
  • 查看本实验室范围的利用率、热力图、趋势与用户履约排名
  • 登记违约（设备损坏、违规使用）与撤销误判并返还信用分

⚙️管理员

  • 实验室 / 设备 / 每周排班（含设备级例外排班）/ 停机计划的全量维护
  • 用户与权限：角色、周额度、负责实验室、冻结解冻、停用、重置口令
  • 23 项业务规则在线配置（签到宽限、扣分标准、信用阈值…），改完即生效
  • 审计日志：谁在何时对什么对象做了什么
  • 运行状态：数据规模、WAL 日志模式、后台作业累计处理量

03冲突规则引擎：把"能不能约"讲清楚

预约校验被拆成 12 条独立规则，按「零成本校验 → 时间窗校验 → 需要查库的区间与额度校验」的顺序短路返回， 每条失败都带机器可读的规则码与中文说明，前端据此做差异化引导。

规则判定内容失败时的用户提示要点
R01设备存在且状态为「可预约」告知设备当前状态（维护中／已停用）
R02所属实验室处于开放状态告知实验室已停用
R03起止时间为合法数值且 start < end时间格式或逻辑错误
R04起点不早于当前时刻不可预约已过去的时间
R05满足最小提前预约分钟数告知需提前多少分钟
R06不超过最大提前预约天数告知最多可提前几天
R07时长在设备 min_minutes ~ max_minutes 内告知该设备的时长上下限
R08请求区间被某一段开放排班完整覆盖告知所选时段不在开放时间内
R09不与停机／校准／封闭计划重叠返回停机原因、类型与起止时间
R10该设备该时段无其它占用（区间重叠检测）返回冲突时段、状态与占用者，并引导加入候补
R11不与本人其它预约重叠返回本人冲突预约的设备与时段
R12账号状态正常、在途数量未超上限、周额度充足返回已用额度与额度上限等明细

📐区间代数（左闭右开）

所有时间区间为 [start, end)：09:00-10:00 与 10:00-11:00 相邻但不冲突，符合真实排期习惯。

// 冲突判定
overlaps(A, B) ⇔ A.start < B.end ∧ B.start < A.end

// 可用时段 = 排班 −（占用 ∪ 停机）
Free(v, day) = Schedule(v, day)
             − Bookings(v) − Blackouts(v)

🔒并发唯一性（20 并发只允许 1 单）

写操作统一走 writeTx()：进程内互斥锁串行化，BEGIN IMMEDIATE 立即取写锁， 并在事务内重新跑一遍完整校验后才插入，彻底消除「先查后写」的竞态窗口。

await acquireWriteLock()   # 进程内互斥
BEGIN IMMEDIATE            # 立即取得写锁
  validateBookingRequest() # 事务内二次校验
  INSERT INTO bookings ...
COMMIT

04技术架构

五层结构，上层可依赖下层、下层不反向依赖；运行时零第三方依赖，无需 npm install。

🧱分层与职责

  • public/ 前端无构建 SPA：api · ui · pages-core · pages-admin · app
  • http/ 传输层请求解析 · Bearer/Cookie 鉴权 · 静态资源 · SPA 回退 · 统一错误
  • routes/ 路由层auth · lab · device · booking · notification · stats · admin（76 个端点）
  • services/ 业务层booking · availability · credit · stats · notification · audit · scheduler · presenters
  • core/ 规则层interval（区间代数）· conflict-rules（R01~R12）· booking-rules（状态机）· config
  • db/ 数据层DatabaseSync · WAL · 写锁 · writeTx / readTx · schema.sql（14 张表）

🛠技术选型与理由

  • 数据库 SQLite（WAL）：单机部署零运维，读写不互斥、写写串行，配合写锁即可保证正确性
  • Web 服务用内置 node:http：手写极简路由器（支持路径参数、区分 404/405），无框架依赖
  • 口令 crypto.scrypt（N=16384, r=8, p=1）加盐散列 + timingSafeEqual 校验
  • 前端零构建：原生 ES Module + 手写 CSS，图表（柱状/环形/热力图）均由 DOM+CSS 实现
  • 后台作业：每 60 秒一轮，处理爽约判定、开始前提醒、候补超时顺延、冻结到期自动解冻
  • 测试框架自研：单进程串行执行，避免受限环境下 fork 子进程失败
